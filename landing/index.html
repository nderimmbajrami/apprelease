How it works

Six steps. Four of them once.

You hand over the repository and the keys one time. After that, releasing is a push.

    Connect GitHub

    Push

apprelease.yaml

Configuration that lives with your code.

A short file in the root of the repository describes the workflow: which Flutter, how to sign, what to build, where to publish. It is reviewed in pull requests like everything else.

  • One workflow per store, or one file per branch.
  • Secrets by reference: the file names a credential, never contains it.
  • Plain shell scripts in between, so nothing is hidden behind a plugin.

Full YAML reference

workflows:
  android-production:
    name: Android · production
    environment:
      flutter: stable
      android_signing:
        - upload_keystore
      groups:
        - google_play
    versioning:
      source: google_play   # next build number comes from the store
    scripts:
      - name: Get packages
        script: flutter pub get
      - name: Build app bundle
        script: |
          flutter build appbundle --release \
            --build-number=$AR_BUILD_NUMBER
    artifacts:
      - build/**/outputs/**/*.aab
    publishing:
      google_play:
        credentials: $GOOGLE_PLAY_SERVICE_ACCOUNT
        track: internal
      email:
        recipients:
          - team@example.com
workflows:
  ios-testflight:
    name: iOS · TestFlight
    environment:
      flutter: stable
      xcode: latest
      ios_signing:
        distribution_type: app_store
        bundle_identifier: com.example.app
    versioning:
      source: app_store_connect
    scripts:
      - name: Get packages
        script: flutter pub get
      - name: Build ipa
        script: |
          flutter build ipa --release \
            --build-number=$AR_BUILD_NUMBER \
            --export-options-plist=$AR_EXPORT_OPTIONS
    artifacts:
      - build/ios/ipa/*.ipa
    publishing:
      app_store_connect:
        auth: integration
        submit_to_testflight: true
        beta_groups:
          - Beta testers

Questions

Questions

Do I need a Mac for the iOS build?

No. iOS builds run on AppRelease's macOS runners with a current Xcode. On the Scale plan you can also register your own Mac as a runner, which is handy if you have one standing around already.

Where are my keys stored?

Keystores, API keys and service accounts are encrypted before they are written to the database. The runner decrypts them into a temporary directory for the duration of one build and removes them when the build ends, whether it passed or failed.

Is this only for Flutter?

Today, yes. The workflows are plain shell scripts, so a React Native or native project builds fine already; what is missing is the guided setup and the quick start. React Native is the next guide we publish.

Is this a full CI service?

No, on purpose. AppRelease is the release step only: sign, version, build, upload. No test matrix, no plugin marketplace, no YAML dialect beyond one page. Keep your CI for tests if you have one, and let AppRelease do the publishing.
