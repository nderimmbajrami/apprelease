How it works

Three steps, then it is routine.

You connect the repository and hand over the signing material once. From then on every release is one click, or one push.

  1. Connect the repository

    GitHub, GitLab, Bitbucket or any Git URL. AppRelease scans the branch for apprelease.yaml and shows the workflows it finds.

  2. Add signing credentials

    Upload the Android keystore, the Google Play service account and the App Store Connect API key. They are encrypted at rest and only ever decrypted on the runner.

  3. Release

    Pick a workflow, a track and a version. Watch the log live. When it is green, the build is on Google Play or TestFlight, and you get an email.

What you get

What you get

Managed code signing

Keystores, provisioning profiles and certificates are fetched for the build and wiped afterwards. Automatic signing through the App Store Connect API, or bring your own files.

Store-based versioning

Before each build the latest build number is read from Google Play or App Store Connect and incremented. No more "this version has already been used".

Tracks and TestFlight

Internal, alpha, beta or production on Google Play. TestFlight groups or a full App Store submission on iOS. Draft submissions for new apps.

Live logs

Every step streams its output as it runs. A failed build tells you which command failed and shows the lines around it, not a 40 MB archive.

Release history

Which commit became which build on which track, who started it and how long it took. Artifacts stay downloadable for 30 days.

Notifications

An email when a release is live or when it fails, with the link to the log. Slack and webhooks are on the way.

apprelease.yaml

Configuration that lives with your code.

A short file in the root of the repository describes the workflow: which Flutter, how to sign, what to build, where to publish. It is reviewed in pull requests like everything else.

  • One workflow per store, or one file per branch.
  • Secrets by reference: the file names a credential, never contains it.
  • Plain shell scripts in between, so nothing is hidden behind a plugin.

Full YAML reference

workflows:
  android-production:
    name: Android · production
    environment:
      flutter: stable
      android_signing:
        - upload_keystore
      groups:
        - google_play
    versioning:
      source: google_play   # next build number comes from the store
    scripts:
      - name: Get packages
        script: flutter pub get
      - name: Build app bundle
        script: |
          flutter build appbundle --release \
            --build-number=$AR_BUILD_NUMBER
    artifacts:
      - build/**/outputs/**/*.aab
    publishing:
      google_play:
        credentials: $GOOGLE_PLAY_SERVICE_ACCOUNT
        track: internal
      email:
        recipients:
          - team@example.com

workflows:
  ios-testflight:
    name: iOS · TestFlight
    environment:
      flutter: stable
      xcode: latest
      ios_signing:
        distribution_type: app_store
        bundle_identifier: com.example.app
    versioning:
      source: app_store_connect
    scripts:
      - name: Get packages
        script: flutter pub get
      - name: Build ipa
        script: |
          flutter build ipa --release \
            --build-number=$AR_BUILD_NUMBER \
            --export-options-plist=$AR_EXPORT_OPTIONS
    artifacts:
      - build/ios/ipa/*.ipa
    publishing:
      app_store_connect:
        auth: integration
        submit_to_testflight: true
        beta_groups:
          - Beta testers

Questions

Questions

Do I need a Mac for the iOS build?

No. iOS builds run on AppRelease's macOS runners with a current Xcode. On the Scale plan you can also register your own Mac as a runner, which is handy if you have one standing around already.

Where are my keys stored?

Keystores, API keys and service accounts are encrypted before they are written to the database. The runner decrypts them into a temporary directory for the duration of one build and removes them when the build ends, whether it passed or failed.

Is this only for Flutter?

Today, yes. The workflows are plain shell scripts, so a React Native or native project builds fine already; what is missing is the guided setup and the quick start. React Native is the next guide we publish.

How is this different from Codemagic or Bitrise?

It does less, on purpose. AppRelease is the release step only: sign, version, build, upload. There is no test matrix, no plugin marketplace, no YAML dialect to learn beyond one page. If you need a full CI, keep it, and let AppRelease do the publishing.
