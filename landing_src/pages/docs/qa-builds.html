QA builds with Slack and Jira

A QA build goes to your testers, not to a store. Push to a branch such as ready-for-qa: the Android APK is posted to your Slack channel, the iOS build goes to TestFlight and is announced there, and the Jira tickets named in the last commit move to Ready for QA.

What happens on a push

  1. GitHub tells AppRelease about the push. The branch matches a rule whose destination is QA build, so one build is queued per platform.
  2. Android: the app is built as a signed release APK (flutter build apk --release) and uploaded to the Slack channel with its version and build number. Nothing goes to Google Play.
  3. iOS: the app is built, uploaded to TestFlight and, once Apple has processed it, announced in the Slack channel with its version and build number. It is never sent to App Store review.
  4. The ticket keys in the last commit message on the branch (for example DAMA-123) are looked up in Jira, listed in the Slack message with their titles, and moved to your QA status.
Slack comes first. A ticket moves only after the build it promises has reached the channel, so nothing says "Ready for QA" without something to test.

Connecting Slack

  1. Open api.slack.com/apps. On the page Your Apps, click Create New App.
  2. Window Create new app: under From scratch, click Paste a manifest, then Continue. Do not pick AI agent or Starter app: they add code this does not need.
  3. Window Create from a manifest: on the JSON tab, select everything in the box and replace it with this text: 
    {
  "display_information": { "name": "AppRelease" },
  "features": { "bot_user": { "display_name": "AppRelease" } },
  "oauth_config": { "scopes": { "bot": ["chat:write", "files:write"] } }
}
    It names the app AppRelease and gives it two permissions: chat:write to send messages and files:write to upload the APK.
  4. Same window: under Workspace, choose your workspace. Click Next, then Create.
  5. Page Allow AppRelease to access Slack: it lists two actions, send messages and upload files. Click Allow.
  6. Window AppRelease is ready!: click the copy icon next to Bot token. It starts with xoxb-. Ignore the App token and the steps under it (Install Slack CLI, Log in, Create your project, Run your app): they are for writing your own bot code. Close the window. Should you need the token again, it is in the app's settings under OAuth & Permissions as Bot User OAuth Token.
  7. In Slack, in the channel where QA should get builds: send /invite @AppRelease. AppRelease is a bot, not a channel: it posts only in channels it is invited to and cannot read messages.
  8. Same channel: click its name at the top. In the window that opens, the Channel ID is at the bottom. It looks like C0123ABCDEF; the #name does not work.
  9. In the console open Credentials → Add credential → Slack (QA builds), paste both and save. Check on the saved connection tells you if a scope is missing or the bot is not in the channel, without posting anything.

Link the connection to one application if each app has its own channel, or leave it Shared for all of them.

Connecting Jira

  1. Open id.atlassian.com/manage-profile/security/api-tokens. On the page API Tokens, click Create API token: the left button, not Create API token with scopes. A token with scopes is refused at your Jira address.
  2. Window Create an API token: type a name, for example AppRelease. Under Expires on, pick the latest date allowed, one year from today; it starts at one week. Click Create.
  3. The next window shows the token. Copy it now: Atlassian shows it only once.
  4. In the console open Credentials → Add credential → Jira (QA tickets) and paste the token under API token.
  5. Jira site: open your Jira in the browser and copy the start of the address, up to .atlassian.net. It looks like https://your-team.atlassian.net.
  6. Atlassian account email: the email you sign in to Jira with, on the same account that made the token. You can read it at id.atlassian.com/manage-profile/email. That account needs permission to move tickets.
  7. Status to move tickets to: in Jira, open any ticket and click its status to see the list. Type the one QA tickets should get, exactly as written there. The default is Ready for QA.
  8. Project keys (optional): the letters before the number of a ticket on your board; for DAMA-123 the key is DAMA. Jira also lists it under Projects, in the Key column. Separate several with commas (DAMA, APP). Then only those tickets are touched, and a lower-case dama-123 in a branch name counts too.
  9. Save, then click Check on the saved connection. It confirms the account and the status without moving a ticket.

There is no board to pick. A ticket is found by the key in your commit, and its status is changed on the ticket itself, so it moves to that column on whichever board shows it. Project keys only narrow which tickets may be moved; leave them empty and every ticket named in a commit is moved.

The token stops working on its expiry date. Create a new one before then and save it on the same connection.

Jira is optional. Without it the Slack message still lists the keys found in the commit; nothing is moved.

Choosing the branch

  1. Open the application → Settings → Release automatically on push.
  2. Add a branch and type ready-for-qa (or your own name; qa/* matches every branch with that prefix).
  3. Tick Android and iOS and choose QA build as the destination of each.
  4. If you have not done so yet, add the webhook shown on that page to the GitHub repository.

Your other rules stay as they are: staging or main keep publishing to the stores. You can also start a QA build by hand: Publish → QA build.

How tickets are found

AppRelease reads the message of the last commit on the branch at the moment it builds. Any of these moves DAMA-123:

git commit -m "DAMA-123 fix the login button"
git commit -m "Login fixes (DAMA-123, DAMA-130)"
git merge DAMA-123-login-button        # "Merge branch 'DAMA-123-login-button' into ready-for-qa"
  • Several keys in one message are all moved.
  • A key that is not a ticket in your Jira (UTF-8, SHA-256) is ignored.
  • A ticket already in the QA status is left alone, so the Android and the iOS build of one push do not get in each other's way.
  • If the Jira workflow has no step from the ticket's status to the QA status, the build still goes out and a second Slack message names the tickets that stayed.

With an apprelease.yaml

No file is needed. If the repository has one, a QA build uses the workflow named android-qa (flavors, another entry point), and ios-qa or else your TestFlight workflow on iOS. Every .apk the workflow lists under artifacts is posted.

workflows:
  android-qa:
    environment:
      android_signing:
        - upload_keystore
    scripts:
      - name: Build QA APK
        script: |
          flutter build apk --release --flavor qa \
            --build-number=$AR_BUILD_NUMBER
    artifacts:
      - build/app/outputs/flutter-apk/*.apk

Common errors

MessageUsually means
The APK has nowhere to goNo Slack connection for this application. Add one under Credentials, shared or linked to the app.
The Slack bot is not in the channelType /invite @AppRelease in the channel.
Slack has no such channel for this botThe channel ID is wrong, or the channel is private and the bot was not invited.
The Slack bot lacks a permissionAdd chat:write and files:write, then reinstall the app to the workspace.
The workflow has no step from "To Do" to "Ready for QA"Jira only allows the moves its workflow draws. Add the transition in Jira, or move the ticket further before pushing.
Jira refused the email and API tokenThe email must be the Atlassian account that created the token.
